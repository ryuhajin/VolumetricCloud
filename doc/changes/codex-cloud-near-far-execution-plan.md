# Codex 실행 계획서
## 근경 구름 형태 복원 · 원경 대기 원근 정상화

- 작성일: 2026-09-19
- 대상: 기존 DirectX 11 / HLSL 볼류메트릭 클라우드 프로젝트
- 문서 성격: 저장소 조사와 비교 실험을 위한 실행 지시서. 현재 코드를 직접 검증한 결과 보고서가 아니다.
- 최우선 목표: **근경의 실제 밀도 형태와 명암을 보존하고, 원경은 카메라까지의 대기 때문에 대비가 낮아지게 한다.**
- 첫 실행 범위: **P0–P2까지만 수행하여 원인과 다음 수정 범위를 보고한다.** 형태·조명·대기 기본값을 한꺼번에 변경하지 않는다.

## 1. 작업 배경과 성공의 정의

### 1.1 사용자가 확인한 현상

카메라에서 가까운 특히 머리 위 방향의 구름이 넓게 번지고 반투명하게 보인다. 반면 수평선 쪽 원경 구름은 상대적으로 또렷하다. 사용자는 가까운 구름의 투과율이 먼 구름보다 높다고 관찰했다. 어떤 투과율을 표시한 것인지는 실제 코드에서 확인한다.

다음 실험은 사용자가 이미 수행했으나 근경 선명도가 크게 개선되지 않았다.

| 실험 | 사용자 보고 |
|---|---|
| 약 5km 이내 View Ray 샘플 간격 감소 | 뚜렷한 개선 없음 |
| Base Noise `Contrast x2` | 뚜렷한 개선 없음 |
| Base Noise `Mid octaves x2.5` | 뚜렷한 개선 없음 |
| `Contrast x2 + Mid x2.5` | 뚜렷한 개선 없음 |

제공된 디버그 화면은 `Base Density`, `Weather Coverage`, `Detail Noise`, `View Transmittance`, `Sun T — Segment Midpoint`다. 각 화면의 출력값·누적 방식·마스크·후처리 여부는 아직 확정하지 않았다. 캡처마다 시간이 달라 정밀한 A/B 근거로 사용하지 않는다.

**이전 실험이 효과가 없었다는 사실을 “더 큰 배율이 필요하다” 또는 “중간 주파수가 반드시 부족하다”로 해석하지 않는다.** 변경이 실제 활성 경로에 들어가지 않았거나, 이후 단계에서 지워졌을 가능성부터 검사한다.

### 1.2 구분할 두 목표

**근경 목표:** 대기를 우회한 구름 원본에서도 윤곽·중간 크기 굴곡·내부 명암이 읽혀야 한다. 밝기만 증가하거나 불투명한 평판으로 바뀌는 것은 성공이 아니다.

**원경 목표:** 같은 원본을 대기 합성 전후로 비교했을 때, 원거리의 명암·색 차이가 대기 투과율과 산란광 때문에 감소해야 한다. 가우시안 블러로 윤곽만 뭉개는 것은 목표가 아니다. 대기 산란광과 투과율은 별개의 합성 항이다.[R2]

머리 위와 수평선은 거리 외에도 관측 방향·통과 길이·보이는 면이 다르다. 모든 근경 구름의 투과율을 모든 원경 구름보다 낮추는 것을 목표로 삼지 않는다. 동일 조건의 통제 실험과 실제 장면의 시각 평가를 함께 사용한다.[R3]

### 1.3 현재 구현으로 단정하지 말 것

과거 대화에서는 대략 다음 구조가 언급되었다.

`Atmosphere LUT → Deep Shadow Cache → Opaque Scene → Cloud → Tone Map`

Aerial Radiance/Transmittance LUT, Near/Far Deep Cache, 높이별 슬라이스, 전체 해상도 구름 패스 등도 언급되었다. **현재 존재 여부, 리소스 종류, 해상도, 슬롯, 함수명, 합성 수식은 저장소에서 재확인한다.** 창 제목의 Stage 번호를 코드 버전이나 활성 품질 경로의 근거로 삼지 않는다.

## 2. 작업 원칙과 금지 사항

### 반드시 지킬 원칙

1. `AGENTS.md`, README, 기존 빌드·테스트·캡처 지침을 먼저 읽는다. 사용자의 미커밋 변경을 보존한다. 무단 reset/clean, 기존 프리셋 덮어쓰기, 원격 push를 하지 않는다.
2. 기존 디버그와 테스트 기능을 재사용한다. 이 문제를 위해 별도 렌더러나 대형 테스트 프레임워크를 새로 만들지 않는다.
3. 한 실험에서는 한 원인군만 변경한다. 모든 비교는 카메라·시간·시드·바람·태양·노출·화이트밸런스·톤매핑·해상도를 고정한다.
4. 진단용 고품질 경로와 출시용 실시간 경로를 구분한다. 느린 기준 영상을 그대로 최종 해결책으로 제출하지 않는다.
5. 근거를 `코드 확인`, `실행 확인`, `가설`, `미검증`으로 구분한다. 실제 실행하지 않은 빌드·캡처·GPU 시간을 성공으로 기록하지 않는다.
6. 대조군을 보존하고 변경을 되돌릴 수 있게 한다. 시각적 기본값 교체는 사용자의 비교 이미지 검토 후 확정한다.

### 하지 말아야 할 임시방편

- 화면 위쪽만 샤프닝하거나 아래쪽만 블러 처리하지 않는다.
- 카메라 거리로 동일 월드 위치의 노이즈 좌표 배율·기본 밀도를 바꿔 문제를 숨기지 않는다.
- `cloudT`만 인위적으로 줄이고 산란광은 기존 값으로 유지하지 않는다.
- 밑면에 무조건 `0.55` 같은 밀도 floor를 넣지 않는다. 구름 영역의 경계와 외부에서는 밀도 0을 유지해야 한다.
- Coverage 분리를 한다면서 `base * coverage`만 다시 쓰고 “면적과 밀도를 분리했다”고 보고하지 않는다.
- 원경 erosion을 0으로 만드는 것을 단순한 디테일 LOD로 취급하지 않는다. 감산 항을 제거하면 구름이 다시 채워질 수 있다.
- 임의의 `0–5km → Mip 0`, `5km 이후 → Mip 3`을 최종 해법으로 고정하지 않는다. 5km는 진단 구간이지 실제 밀도 모델의 경계가 아니다.
- Unreal 문서의 머티리얼 노드·콘솔 명령을 이 프로젝트의 실제 HLSL 함수로 가정하지 않는다.

## 3. 전체 작업 순서와 분기

| 단계 | 목표 | 다음 단계로 넘어가는 조건 |
|---|---|---|
| P0 | 활성 코드 경로와 재현 기준 확보 | 현재 상태를 동일 조건으로 다시 재현할 수 있다. |
| P1 | 기존 파라미터가 실제 GPU 결과에 영향을 주는지 확인 | 값 전달·생성·바인딩·밀도 계산 경로가 검증된다. |
| P2 | 밀도 / 적분·복원 / 조명 / 대기 문제 분리 | 원인 후보별 지지·반박 근거와 수정 우선순위가 있다. |

| P4 | 필요한 경우에만 근경 조명·그림자 수정 | 원본 형태가 조명에서도 읽히며 과도한 채움광이 없다. |
| P5 | 원경 대기 조회·합성 정상화 | 거리별 대기 수치와 실제 합성 결과가 일치한다. |

P3–P5를 모두 수정해야 하는 것은 아니다. P2에서 정상으로 확인된 부분은 유지한다. 예를 들어 재구성 버그가 원인이면 밀도 모델을 다시 만들지 않는다. 대기 오류가 확인되면 형태 튜닝보다 먼저 고쳐도 된다.

## P0. 저장소 조사와 베이스라인 확보

### 실행

**저장소와 실행 경로**

- 현재 브랜치·커밋·미커밋 변경 목록, 빌드 설정, 실제 실행 파일 경로를 기록한다.
- CPU 설정 → 상수버퍼/텍스처 생성 → View 밀도 평가 → Sun 밀도 평가/캐시 → 구름 적분 → 대기 합성 → 복원/톤매핑의 실제 파일·함수를 찾는다.
- View와 Sun 경로가 같은 밀도 정의를 쓰는지, 어떤 LOD·근사만 다른지 구분한다.
- 노이즈 텍스처, 그림자 캐시, 대기 LUT의 dirty/hash/generation 갱신 조건을 확인한다.
- 디버그 항목별로 원본 한 점, 고정 단면, 첫 유효 샘플, 가중 평균, 누적량 중 무엇을 표시하는지 기록한다. 색 팔레트와 톤매핑도 확인한다.

**재현 장면**

기존 카메라 프리셋을 우선 사용하여 다음 세 장면을 저장한다.

| ID | 장면 | 목적 |
|---|---|---|
| C0 | 문제가 보이는 머리 위 근경 | 주된 개선 대상 |
| C1 | 근경과 원경이 함께 보이는 사선 시점 | 거리감과 전이 확인 |
| C2 | 수평선 중심 원경 | 대기·원거리 LOD 확인 |

가능하면 같은 구름 덩어리의 밑면과 옆면을 보는 보조 시점도 저장한다. 원경의 다른 구름과 단순 비교하는 대신 관측 면의 차이를 확인하기 위한 것이다.

**측정 조건**

실제 화면 크기, 구름 Trace RT 크기, 재구성 RT 크기, 모든 픽셀의 당프레임 계산 여부를 따로 기록한다. 전체 해상도 창이라고 전체 해상도로 추적한다고 가정하지 않는다.[R1]

기존 GPU 예산을 찾아 기록한다. 과거 대화의 숫자를 현재 승인 예산으로 자동 채택하지 않는다. 예산을 찾지 못하면 현재 p50/p95와 후보 증감률을 보고하고 성능 승인 여부를 미정으로 둔다.

### 산출물 / 통과 기준

`baseline.md`, 카메라·설정 스냅샷, 원본 캡처, 활성 경로 표를 만든다. 동일 설정으로 재실행했을 때 비교 가능한 장면이 재현되어야 한다.

## P1. “조정했는데 변화가 없다”의 전달 경로 검증

### P1-A. CPU 값이 실제 사용되는지 추적

`Contrast`, `Mid octaves`, 근거리 step 관련 값 각각에 대해 다음을 추적한다.

`UI/설정 → CPU 값 → 생성 설정 또는 상수버퍼 → 실제 GPU 리소스 → 활성 셰이더 분기 → 최종 밀도`

상수버퍼 슬롯·C++/HLSL 오프셋·크기·업데이트 시점을 확인한다. 필요하면 Shader Reflection이나 기존 검증 코드를 사용한다. HLSL 상수버퍼 패킹을 C++ 배치와 동일하다고 가정하지 않는다.[R7]

노이즈 생성 파라미터라면 dirty/hash에 포함되는지, candidate 리소스가 실제 교체되는지, 수정한 텍스처와 렌더러가 읽는 SRV가 같은지 확인한다. 원본이 바뀌었는데 하위 Mip만 예전 데이터인지도 검사한다.

### P1-B. 단면과 고정 월드 좌표로 영향 측정

전체 화면 인상만 비교하지 않는다. 동일 시드에서 고정된 XZ/Y 단면과 월드 샘플 집합을 골라 다음 값을 전후 비교한다.

- Base 원본, Mid 기여, Weather/Height 적용 후, Detail 적용 전후의 밀도.
- 최종 소광계수, 해당 샘플의 LOD, 실제 텍스처 generation 식별값.
- 변화한 샘플 비율, 차이의 평균/최댓값, 0 또는 상한으로 포화되는 비율.

포화되지 않은 유효 구간을 포함해야 한다. Mid 가중치를 바꿔도 정규화나 clamp 때문에 영향이 작아질 수 있으므로 그 수식을 함께 기록한다.

필요할 때만 일회성 진단 토글로 활성 밀도 입력을 분명한 상수/합성 패턴으로 바꾸어 경로를 검증한다. 진단을 마치면 제거하거나 기본 OFF로 되돌린다.

### P1-C. 근거리 step 변경의 유효성

정규화된 `rayDir` 기준으로 `p = cameraPos + t * rayDir`에서 t가 카메라부터의 거리인지 확인한다. `t - tStart`나 월드 높이를 카메라 거리로 사용하지 않는지 검사한다.

각 ray에 대해 실제 ds 범위·샘플 수·마지막 t·종료 사유를 확인한다. 작은 step 때문에 최대 반복 횟수에 먼저 도달하면 전체 구간을 적분한 것이 아니다. coarse skip이 그대로 커서 세부 구조를 넘기는지도 검사한다.

구간 투과율은 실제 구간 길이를 포함해야 한다.

```text
segmentT = exp(-sigmaT * ds)
cloudT  *= segmentT
```

균일 매질에서 ds를 줄여도 같은 전체 구간의 T는 수렴하며 거의 같아야 한다.[R3] 산란광 적분도 같은 ds 정의를 사용해야 한다.

### 통과 기준

각 파라미터가 어디까지 영향을 주는지 코드와 수치로 설명할 수 있어야 한다. 미연결 파라미터, 오래된 텍스처, 잘못된 바인딩, 구간 잘림이 발견되면 최소 수정 후 P0 비교를 반복한다. 그 전에는 노이즈 배율을 더 올리지 않는다.

## P2. 흐려지는 단계 분리

### P2-A. 원본 참조 모드

기존 설정으로 다음 조건의 진단 모드를 구성한다. 가능하면 C0의 작은 ROI부터 시작한다.

- 실제 Trace RT를 화면 해상도와 맞추고 모든 픽셀을 당프레임 계산한다.
- 시간적 히스토리, 공간 블러, 업샘플링, 샤프닝, 동적 해상도를 우회한다.
- 노출·톤매핑을 우회한 선형 데이터도 저장한다.
- 진단용으로 Base/Detail의 원본 Mip을 비교한다. SRV의 MostDetailedMip와 샘플러 LOD 제한도 확인한다.[R4]
- jitter와 바람을 고정한다. 고품질 기준은 step을 단계적으로 줄여 결과 수렴을 확인한다.

이미 해당 기능이 없는 프로젝트라면 새로운 기능을 만든 뒤 끄는 일을 하지 않는다. 현재 경로에 없다고 기록하면 된다.

### P2-B. 최소 비교 출력

| 출력 | 확인할 내용 |
|---|---|
| 원본 노이즈 단면 + 최종 밀도 단면 | 생성된 변화가 밀도까지 전달되는가? |
| `cloudT`, `1-cloudT` | 조명을 제외한 실루엣과 중심부 불투명도는 어떠한가? |
| 대기 전 Cloud Radiance | 형태가 빛과 그림자로 읽히는가? |
| 직접광 / 환경광 / 다중 산란 분리 | 어떤 항이 명암 대비를 줄이는가? |
| cloud distance / `T_air` / `S_air` | 근·원거리 구분과 대기 조회가 실제로 맞는가? |
| 최종 합성 전·후 | 합성/복원에서만 흐려지는가? |

기존 출력이 있다면 재사용한다. 한 번에 모든 항목용 UI를 신설하지 말고 필요한 출력만 순차 추가한다. `Sun T — Segment Midpoint` 한 장만으로 전체 구름 자체 그림자의 품질을 판정하지 않는다.

### P2-C. 알려진 형상의 대조 실험

현재 Weather/Base/Detail 대신 고립된 균일 구 또는 타원체를 넣어 동일 View 적분·합성 경로로 렌더한다. 조명·대기를 우회한 T부터 확인한다.

균일 구 내부를 통과한 정확한 길이 L을 ray–sphere 교차로 계산하면 참조값은 다음과 같다.

```text
T_reference = exp(-sigmaT * L)
```

이는 노이즈와 무관하게 적분 정확도를 검사하는 기준이다.[R3] step 감소에 따른 오차 수렴을 확인한다. 그다음 유한한 경계 전이 폭을 가진 형태로 경계 보존을 확인한다.

알려진 형태도 최종 영상에서만 번지면 밀도 노이즈를 다시 만드는 것이 우선이 아니다. 알려진 형태는 잘 보이는데 현재 구름만 흐리면 실제 밀도 구조 쪽의 근거가 된다.

### P2-D. 대기만의 독립 검사

구름 모양과 별개로, 지면을 관통하지 않는 동일 카메라 ray의 2/5/10/20km 등 유효 거리에서 Aerial LUT 값을 조회한다. 이 거리는 진단 예시이며 LUT의 실제 범위와 함께 기록한다.

동일 ray에서 거리를 늘릴 때 `T_air`가 수치 오차 범위 밖에서 증가하지 않는지 확인한다. 서로 다른 고도·시선의 두 픽셀을 비교해 단조성을 강요하지 않는다.

같은 위치에 가상의 밝은 입력과 어두운 입력을 각각 합성하여, 선형 RGB에서 다음 관계를 확인한다.

```text
outBright - outDark = T_air * (inBright - inDark)
```

이 실험은 원거리 대비 감소 경로가 작동하는지 검사한다. 실제 구름 모양이 나쁘다는 이유로 대기 버그가 가려지지 않게 한다.

### 판정표

| 결과 | 우선 수정 |
|---|---|
| 파라미터가 실제 데이터까지 전달되지 않는다. | P1 전달·갱신 경로 |
| 알려진 구도 T 또는 경계가 잘못 나온다. | 적분·깊이·재구성·합성 |
| 구는 정상이나 최종 구름 밀도 자체가 완만하다. | P3 밀도 구조 |
| 밀도/알파는 충분하나 빛을 넣으면 밋밋하다. | P4 조명·그림자 |
| 대기 독립 검사에서 거리·감쇠 관계가 틀리다. | P5 대기 조회·합성 |
| 고품질 원본은 정상이고 실시간 경로만 흐리다. | P6 재구성·LOD |

### 1차 보고 게이트

P0–P2 완료 후 **확인된 사실, 아직 남은 가설, 효과 없는 원인 후보, 다음 한 가지 수정**을 제출한다. 근경 형태·대기 기본값을 대규모로 바꾸지 않은 상태에서 사용자 검토를 받는다.

## P3. 근경 밀도 구조 개선 — 증거가 있을 때만

### P3-A. 누적 감쇠를 수치로 확인

동일 월드 단면에서 다음 단계를 순서대로 출력한다.

`Weather/Coverage → Base shape → Mid structure → Height/Bottom/Top → Erosion → Density amplitude → sigmaT`

실제 코드 순서가 다르면 그 순서로 기록한다. 특정 순서를 강제로 맞추지 않는다. 특히 밑면의 여러 곱셈이 겹쳐 유효 코어가 사라지는지 확인한다.

`bottomFadeEnd = 0.08` 같은 정규화 값뿐 아니라 각 위치의 실제 구름 두께에 곱한 미터 단위 폭도 기록한다. 가변 두께라면 단일 고정 폭이라고 보고하지 않는다.

### P3-B. 후보 D1 — 코어와 경계 전이 분리

원인 근거가 있으면 경계 바깥을 0으로 유지하면서, 내부가 충분한 밀도에 도달하도록 Height/Bottom 프로파일의 전이 폭·중복 감쇠를 조절한다.

기존 프로파일과 “전이 폭만 축소한 후보”를 비교한다. 전체 공간에 최소 밀도를 추가하지 않는다. 밑면이 수평 판처럼 잘리거나 카메라 진입 시 경계가 나타나면 탈락이다.

Coverage가 존재 영역과 밀도 크기를 동시에 제어하고 있다면 역할을 문서화한다. 필요할 때만 존재 영역은 threshold/remap·footprint로, 내부 밀도는 별도 amplitude로 제어하는 후보를 비교한다. Coverage를 곱하는 구현 자체가 무조건 틀렸다고 전제하지 않는다.

### P3-C. 후보 D2 — Mid 구조의 크기와 영향 위치 수정

기존 Mid 밴드가 실제로 존재하는데 약한 것인지, 월드 크기가 너무 큰 것인지, 높이 마스크 이후 사라지는 것인지 먼저 구분한다.

텍스처 해상도, 월드 반복 폭, 생성 주파수, 실제 샘플 LOD를 따로 기록한다. 진단용 고정 좌표 배율 1/2/4 등의 비교를 통해 적절한 공간 크기를 찾되, 같은 월드 지점의 좌표를 카메라 거리로 바꾸지 않는다.

새 샘플을 추가하기 전에 기존 밴드의 좌표 스케일과 결합 위치를 조절한다. 그래도 필요한 형태가 없다는 근거가 있을 때만 독립 Mid 밴드를 추가한다. 노이즈 스케일과 강도는 별도 제어 항목이다.[R6]

### P3-D. 후보 D3 — 코어를 보존하는 경계 침식

Detail이 이미 옅은 코어까지 제거한다는 근거가 있으면, 큰 형태를 유지하고 낮은 밀도의 주변부에서 주로 침식하는 후보를 만든다.

아래는 구조를 설명하는 의사코드다. 프로젝트에 그대로 덮어쓰지 않는다.

```text
shape = BuildBoundedBaseAndMid(worldPosition)
edgeWeight = ComputeErosionWeight(shape)
eroded = max(shape - edgeWeight * erosionAmount * detail, 0)
density = domainSupport * heightProfile * densityAmplitude * eroded
```

- `domainSupport`는 허용 영역의 경계와 외부에서 0을 보장한다.
- 위 이름과 실제 적용 순서는 예시다. 같은 Height 마스크를 중복 적용하지 않는다.
- 한 점의 낮은 밀도를 엣지로 보는 것은 근사다. 고립된 얇은 내부 구조까지 불필요하게 없애지 않는지 확인한다.
- 코어를 키웠다는 이유만으로 합격시키지 않는다. 실제 중간 굴곡과 자연스러운 경계를 평가한다.

### P3-E. 동기화와 건너뛰기 조건

밀도가 바뀌면 관련 그림자 캐시와 히스토리를 무효화한다. 소광 배율이 달라질 때도 산란 계산과의 일관성을 유지한다.

Mid 추가로 기존 Base 밖에 밀도가 생길 수 있다면 coarse occupancy/empty-space skip의 보수성도 갱신한다. **실제 밀도가 양수인 곳을 cheap 검사에서 비었다고 판정하면 안 된다.** 최적화 없는 참조 밀도와 비교한다.[R1]

### 통과 기준

대기·후처리를 끈 동일 근경 ROI에서 개선이 보여야 한다. `density outside domain = 0`, 안정된 coverage, 자연스러운 밑면, 카메라 이동 시 형태 고정, 그림자와의 일치가 유지되어야 한다. D1–D3는 각각 비교한 뒤 근거가 있는 조합만 남긴다.

## P4. 근경 조명·자체 그림자 개선 — 필요한 경우만

### 실행

현재 근경 ROI에서 캐시 Sun T와 고품질 직접 태양 적분을 비교한다. 직접 적분은 동일한 기본 밀도 정의를 사용하고, step을 줄여 참조 수렴을 확인한다. 별도의 다른 구름을 그리는 식의 비교를 하지 않는다.

직접 적분에서만 굴곡 명암이 살아난다면 캐시 범위·월드 텍셀 크기·슬라이스 간격·필터 폭·사용 LOD를 조사한다. 전역 캐시 해상도를 무조건 높이지 않는다. 광선 적분과 그림자 맵/캐시의 품질·비용은 분리해서 평가한다.[R1]

가능한 후보는 다음 순서로 하나씩 비교한다.

| 후보 | 적용 근거 |
|---|---|
| 캐시 조회·좌표·보간 오류 수정 | 직접 적분과 구조적으로 다른 결과 |
| Near 캐시 범위·해상도 재배분 | 해상도 부족이 확인됨 |
| 근거리 짧은 직접 적분 + 먼 구간 캐시 | 국소 차폐만 부족하고 비용 여유가 있음 |
| 환경광·다중 산란의 채움 정도 조정 | 개별 직접광은 정상인데 합친 뒤 대비가 사라짐 |

하이브리드 구현에서는 구간을 겹쳐 적분하지 않는다. 같은 광선의 분리된 구간이라면 `T_total = T_near * T_far`이고 `tau_total = tau_near + tau_far`다.[R3] 기존 전체 광학 깊이에 근거리 값을 그냥 더하지 않는다. 캐시의 실제 의미가 이 구간 분해를 지원하는지 먼저 확인한다.

다중 산란의 이름만 보고 임의로 감소시키지 않는다. 실제 함수의 contribution/occlusion 의미를 확인하고, 태양·하늘·지면·다중 산란을 분리해 비교한다. 밀도와 전역 노출을 동시에 바꾸지 않는다.

### 통과 기준

내부 굴곡이 읽히면서 구름이 과도하게 검거나 딱딱해지지 않아야 한다. Near/Far 전환, 낮은 태양 고도, 카메라 이동에서 경계·밴딩이 없어야 한다. 비용 증가와 오차 감소를 함께 보고한다.

## P5. 원경 Aerial Perspective 조회·합성 정상화

### P5-A. 거리와 LUT 계약

카메라→구름의 대기와 태양→구름의 대기를 구분한다. 태양 입력 색만 바꿔 원경 대기 문제가 해결됐다고 보고하지 않는다.

다음 항목을 실제 코드로 확인한다.

- 카메라부터의 거리인가, 도메인 진입 후 이동 길이인가?
- ray의 t, view-space Z, 정규화 깊이 중 무엇을 사용하는가?
- 월드 단위와 LUT 단위의 m/km 변환은 정확한가?
- 생성 시 거리 분포와 조회 시 역매핑이 대응하는가?
- 카메라 방향·FOV·고도·원점이 LUT 생성 좌표와 일치하는가?
- 최대 거리 이후 마지막 슬라이스만 읽고 있지 않은가?
- 카메라 이동·대기 파라미터 변경 후 올바르게 갱신되는가?

LUT의 범위·깊이 슬라이스와 실제 조회 위치는 구분해야 한다.[R2]

### P5-B. 구름 대표 거리

`tStart`, `tEnd`, `(tStart+tEnd)/2`를 실제 보이는 구름 거리로 무조건 사용하지 않는다.

현재 방식의 문제가 확인되면 다음 가중 대표 거리를 후보로 비교한다.

```text
weight_i = T_cloud_before_i * (1 - T_cloud_segment_i)
dRep = sum(weight_i * sampleDistance_i) / sum(weight_i)
```

이는 불투명도 기여를 기준으로 여러 깊이를 한 값으로 압축하는 근사다. 산란광의 정확한 발생 위치 분포와 동일하지 않다. 분모가 거의 0인 구름 없는 픽셀은 거리 무효로 표시하고 정상 배경을 반환한다.

근경과 원경 구름이 크게 겹치는 픽셀에서 대표 거리 하나의 오차가 확인될 때만 구간별/다층 합성을 검토한다. 검증 없이 전 화면에 고비용 대기 적분을 추가하지 않는다.

### P5-C. Premultiplied 색과 대기의 합성

먼저 현재 저장값의 정의를 문서화한다. 다음 식은 아래 전제에서만 사용하는 대표 거리 근사다.

- `C`: 구름 자체의 투과율/구간 기여를 이미 반영해 누적한 산란광. 카메라까지의 대기는 아직 미반영.
- `Tc`: 구름 자체의 최종 스칼라 투과율.
- `B`: 구름이 없을 때의 배경. 카메라에서 본 대기 효과가 이미 포함됨.
- `Ta`, `Sa`: 카메라부터 대표 구름 위치까지의 대기 투과율과 산란광.

```hlsl
// 계약 설명용 의사코드. 실제 저장값과 다른 경우 그대로 적용하지 않는다.
float3 result = Tc * B + Ta * C + (1.0 - Tc) * Sa;
```

Premultiplied 누적색에 alpha를 다시 곱하지 않는다. 배경 하늘의 대기 효과를 중복 적용하지 않는다. 모든 항은 같은 기준의 선형 HDR/노출 스케일을 사용한다. 볼륨 합성에서는 누적색의 불투명도 가중 여부와 블렌딩 계약이 일치해야 한다.[R5]

필수 경계 테스트:

| 입력 | 기대 결과 |
|---|---|
| 구름 없음: `Tc=1`, `C=0` | `B` 그대로 |
| 대기 없음: `Ta=1`, `Sa=0` | `C + Tc*B` |
| 불투명 구름: `Tc=0` | `Ta*C + Sa` |
| 구름색이 이미 대기 포함 | 위 식을 다시 적용하지 않음 |

### P5-D. 정상화 후에만 아트 조정

조회·합성이 정상인 뒤 기존 대기의 거리 배율, 산란량, 높이 분포 중 필요한 항목을 하나씩 조절한다. 조정 가능한 대기 거리 배율과 산란 파라미터는 실제 엔진에도 별도로 존재한다.[R2]

효과를 과장한 테스트는 연결 검사 용도이고, 최종값은 가까운 2–5km 구름까지 과하게 씻어내지 않는 수준으로 결정한다. `T`만 임의 제곱하고 산란광은 이전 값으로 두는 식의 불일치를 만들지 않는다.

### 통과 기준

P2-D의 대기 독립 검사를 통과하고, 동일 원경 구름의 AP OFF/ON에서 대비 감소가 확인되어야 한다. AP를 끈다고 구름 자체의 밀도·광학 두께가 달라져서는 안 된다. 빈 하늘, 태양 원반, 건물 경계에 추가적인 후광·이중 안개가 없어야 한다.

## P6. 실시간 품질·LOD·재구성 복원

### 복원 순서

P2의 고품질 기준을 유지한 채 기존 최적화를 하나씩 복원한다.

`공간 필터/LOD → adaptive step/skip → 저해상도 tracing/upsample → temporal reconstruction`

프로젝트에 실제로 존재하는 항목만 수행한다. 각 복원 직후 근경 ROI와 카메라 이동 영상에서 기준과의 차이를 비교한다.

### LOD와 step

거리만으로 Mip을 고정하는 대신, 투영된 샘플 영역과 ray step이 월드에서 대표하는 범위를 기준으로 LOD를 검토한다. 중점 부근의 대략적인 픽셀 폭은 다음 식으로 가늠할 수 있다.

```text
pixelWidthWorld ≈ 2 * distance * tan(verticalFov / 2) / traceHeightPixels
```

이는 중심 투영의 크기 추정식이며 화면 전체나 모든 방향에서 정확한 footprint는 아니다. 필요하면 인접 ray의 월드 샘플 차이로 축별 크기를 추정한다. Trace RT의 실제 해상도를 사용한다.

`SampleLevel`의 숫자를 키우면 더 높은 Mip을 선택한다.[R4] 하지만 원시 노이즈의 Mip 평균 후 비선형 threshold/erosion을 적용하면, 최종 밀도를 평균낸 결과와 같지 않을 수 있다. 따라서 Mip을 바꿔도 전체 구름량이 보존된다고 가정하지 않는다.

동일 덩어리에서 LOD 변화 전후의 투과율 분포와 보이는 면적을 비교한다. 카메라 이동 시 팽창·수축·깜빡임이 나타나면 필터링과 밀도 결합을 재검토한다.

### 재구성

원본은 선명한데 temporal 경로에서만 흐려지면 motion/reprojection 위치, 구름 깊이, 바람 이동 보정, disocclusion, history weight/clamp를 검사한다. 조명 없는 알파와 빛이 포함된 색의 히스토리 계약도 확인한다.

카메라 고정 상태만 통과시키지 않는다. 천천히 회전·전진하는 구간과 빠른 카메라 전환을 모두 검사한다. 마지막 샤프닝으로 앞 단계 오류를 덮지 않는다.

### 통과 기준

고품질 기준 대비 형태를 유지하면서 기존 승인 예산을 만족한다. 숫자로 정해진 기존 예산이 없다면 baseline 대비 GPU 증감과 품질 손실을 제출하고 임의로 성능 합격을 선언하지 않는다.

## P7. 최종 검증·산출물·승인

### 비교 세트

| 세트 | 비교 | 목적 |
|---|---|---|
| A | Baseline / 최종 후보, 대기 OFF | 근경 자체 형태 개선 |
| B | 동일 후보, 대기 OFF / ON | 원경 변화가 대기 때문인지 확인 |
| C | 참조 고품질 / 실시간 경로 | 샘플링·복원의 품질 손실 |
| D | 정지 / 회전 / 전진 영상 | swimming·ghosting·LOD popping |
| E | 중간 태양 고도 / 낮은 태양 고도 | 그림자 밴딩·원경 과대 감쇠 |
| F | 빈 하늘 / 성긴 구름 / 조밀한 구름 | 대기 중복·캐시·보수적 skip 회귀 |

### 기록할 수치

- 근경 ROI의 실제 `T_cloud`/alpha 분포와 중심부 대표값.
- 같은 경계 구간의 정규화된 10–90% 전이 폭. 반투명 구름에서는 국소 최대 alpha로 정규화한 폭과 원래 최대 alpha를 함께 기록한다.
- 동일 ROI의 선형 휘도 대비와 밝기 평균. 밝기 증가만으로 성공을 판단하지 않는다.
- 원경 AP OFF/ON의 대비 감소, 거리별 `T_air`/`S_air` 샘플.
- 동일 조건에서 Cloud/Shadow/Atmosphere/Total GPU의 p50/p95, 리소스 메모리 증가량.

p50/p95는 예를 들어 워밍업 120프레임 후 300프레임 이상을 3회 측정한다. 이 수치는 프로젝트 기존 규칙이 없을 때 쓰는 제안 프로토콜이다. 컴파일·텍스처 재생성 프레임은 steady-state와 별도로 기록한다. 실제 측정 프레임 수와 GPU/드라이버/빌드 설정을 함께 남긴다.

가까운 구름과 먼 구름의 경계 픽셀 폭을 그대로 비교하지 않는다. 투영 크기가 다르므로 주로 동일 카메라의 수정 전후를 비교하고, 거리 비교는 동일 형상의 통제 장면을 별도로 사용한다.

### 최종 실패 조건

아래 중 하나라도 남으면 완료라고 보고하지 않는다.

- 근경을 두껍게만 만들어 매끈한 평판이나 벽처럼 보인다.
- 원경만 블러 처리해 상대적으로 근경이 좋아 보이게 만들었다.
- 카메라 이동에 따라 월드 구름 자체가 변형된다.
- 밀도와 그림자가 다른 구름을 나타내거나 캐시 경계가 보인다.
- 빈 하늘에 대기가 두 번 적용되거나 반투명 구름색에 alpha가 두 번 적용된다.
- 고품질 캡처만 제출하고 실시간 경로의 품질/비용을 검증하지 않았다.
- 실행하지 않은 테스트를 통과로 표기했다.

### 파일과 보고 형식

기존 저장소 규칙에 맞추되, 예시는 다음과 같다.

```text
docs/cloud-near-far/
  baseline.md
  investigation.md
  experiments.md
  final-report.md

artifacts/cloud-near-far/
  baseline/
  reference/
  density/
  lighting/
  aerial/
  final/
  settings.json
  metrics.csv
```

큰 캡처·영상은 기존 산출물 정책을 따른다. 자동으로 Git에 모두 넣지 않는다.

각 실험은 다음 템플릿으로 기록한다.

```text
실험 ID / 단계:
검사하는 가설:
변경한 파일·함수·설정:
고정한 조건:
예상 결과:
실제 실행 결과와 파일:
수치 / GPU 비용:
판정: 채택 / 기각 / 추가 확인
남은 한계와 되돌리는 방법:
```

최종 보고서는 “무엇을 몇 배 올렸다”보다 **어느 단계에서 정보가 사라졌고, 어떤 증거로 원인을 확인했으며, 수정이 근경과 원경에 각각 어떻게 작용하는지**를 중심으로 작성한다.

## 4. 첫 실행에 대한 Codex 지시문

아래 범위로 시작한다.

> 이 문서를 기준으로 P0–P2까지만 먼저 실행해라. 기존 AGENTS.md와 작업 규칙을 따르고 사용자 변경을 보존해라. 먼저 활성 셰이더 경로와 기존 Contrast/Mid/step 파라미터가 실제 GPU 데이터에 영향을 주는지 확인해라. 카메라·시간·바람·노출을 고정하고, 원본 밀도·T·대기 전 색·대기 조회·최종 복원을 분리해 비교해라. 필요하면 알려진 구/타원체 밀도를 대조군으로 사용해라. 새 노이즈 밴드, 전역 밀도 floor, 원경 블러, 대규모 캐시 재설계는 아직 하지 마라. 증거가 확인된 최소 기능 수정은 가역적으로 수행하고 기록하되, 시각적 기본값은 바꾸지 마라. 실제 실행할 수 없는 항목은 미검증으로 표시해라. 완료 후 확인된 원인과 남은 가설, 수정 후보 하나, 비교 캡처·수치·실행 명령을 보고해라. 그 보고를 검토한 뒤 필요한 P3–P6 작업 범위를 확정한다.
